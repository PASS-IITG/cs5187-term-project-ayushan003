## Description

Executing LPAD() or RPAD() with a length argument of 9223372036854775807 causes the Turso process to abort due to a failed memory allocation.

Instead of returning a SQL error, the process terminates with SIGABRT.

This is reproducible with both functions.

## Steps to Reproduce

Start Turso with an in-memory database:

./target/release/tursodb :memory:

Execute:

SELECT LPAD('a', 9223372036854775807, 'b');

The process aborts with:

memory allocation of 9223372036854775806 bytes failed
Aborted (core dumped)

Exit code: 134

The same behaviour occurs with:

SELECT RPAD('a', 9223372036854775807, 'b');

## Expected Behaviour

The database should handle the oversized requested string gracefully by returning a SQL error, rather than aborting the entire process.

## Actual Behaviour

The attempted allocation causes the process to terminate with SIGABRT. The database session is lost.

## Additional Observations

The issue is not reproduced with every large length.

For example:

SELECT LPAD('a', 4294967296, 'b');

Returns:

Runtime error: string or blob too big (18)

Normal padding operations also work:

SELECT LPAD('a', 10, 'b');
SELECT RPAD('a', 10, 'b');

Both return the expected padded strings.

## Investigation Notes

Both LPAD() and RPAD() use the shared pad() implementation in:

core/functions/string.rs

The failure was initially discovered through SQL fuzzing and subsequently reproduced manually using a fresh in-memory database.

Both functions independently reproduce the crash.
